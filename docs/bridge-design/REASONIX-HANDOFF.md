# Reasonix 实施交接说明

## 1. 你的任务

你负责按照本目录的设计文档，分阶段实现本地多 Agent 协调器。产品目标不是让模型在后台自动互调 API，而是协调用户手动打开的 Codex、Reasonix 及其他 Agent：强模型负责规划、疑难升级和最终审查，低成本模型承担大量实现工作。

## 2. 设计权威顺序

1. 本目录已批准的设计文档。
2. 当前阶段由用户明确补充的要求。
3. 现有程序中与前两项不冲突的行为。

遇到冲突或关键空白时停止并提问，不自行扩大范围。不得把 Agent 数量写死为两个，也不得用 Markdown 文件替代 SQLite 事实源。

## 3. 开始前

- 阅读 [设计索引](00-README.md) 及其链接的全部文档。
- 检查现有代码、测试、依赖和未提交改动；不得覆盖用户工作。
- 给出当前阶段的文件级计划、测试计划和风险点。
- 只执行用户明确指派的阶段。

## 4. 实施纪律

- 测试先行：先写能证明需求和缺陷的测试，再写最小实现。
- 核心规则集中在可测试模块，不放进 GUI 事件处理器。
- Git、验证、通知和 Agent 提示通过适配器隔离。
- 所有状态迁移、权限判断、危险确认和外部操作都可审计。
- 外部命令使用参数数组，禁止拼接任意 shell 文本。
- 路径必须规范化并验证范围；清理、覆盖、回滚前执行安全检查。
- 不提交凭据、运行数据库、日志、本机路径或 Agent 产生的临时成果。
- 未获得批准不得执行破坏性 Git 操作或删除工作区。

## 5. 每阶段停止点

完成一个 Phase 后停止，不自动进入下一阶段，并提交：

- 完成内容与未完成内容
- 设计偏差
- 修改文件
- 测试命令及未经删减的结果摘要
- 手工验收证据
- 已知缺陷、安全与迁移影响
- 提交哈希

若测试不能运行，必须报告真实原因，不能以静态阅读代替通过声明。

## 6. 禁止的捷径

- 不得仅生成两个对话用 Markdown 文件就声称实现多 Agent 桥接。
- 不得信任回执中的 `COMPLETED` 文本而跳过身份、租约、范围和验证检查。
- 不得让不同 Agent 默认共用同一可写工作树。
- 不得在冲突时自动选择一方覆盖另一方。
- 不得用吞异常、无界重试或删除锁文件掩盖恢复问题。
- 不得为了降低 token 而省略必要的安全上下文、验收条件或 diff 证据。

## 7. Codex 验收方式

Codex 将按以下顺序审查：

1. 对照当前阶段范围检查设计覆盖率。
2. 阅读代码与迁移，寻找越权、竞态、覆盖和恢复风险。
3. 运行单元、集成、端到端和安全测试。
4. 使用真实临时 Git 仓库复现多 Agent 流程。
5. 检查 Markdown/JSON 协议能否桥接 2 个及多个 Agent。
6. 验证低成本执行、强模型升级与最终审查的成本闭环。

只有证据通过才批准下一阶段。
