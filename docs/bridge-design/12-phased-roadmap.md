# 12. 分阶段实施路线

## 总体规则

按阶段交付，禁止一次性重写。每一阶段都要先提交测试，再提交最小实现；阶段未通过验收不得进入下一阶段。Reasonix 每阶段完成后停止，提交证据供 Codex 审查。

## Phase 0：测试地基与现有程序解耦

目标：在不新增业务能力的前提下，使现有核心可以被自动测试。

范围：

- 建立测试框架、CI 命令和固定 fixtures。
- 记录现有可见行为，补充回归测试。
- 将 GUI、协调核心、文件 I/O 和外部命令边界分开。
- 建立一条命令运行全部本地测试的入口。

验收：现有关键行为有测试保护；GUI 不再承载核心业务规则；测试无需人工点击即可运行。

## Phase 1：协议、数据库与状态机核心

目标：形成可恢复、可审计的本地任务事实源。

范围：

- SQLite schema、迁移、事件和单实例锁。
- 项目、Agent profile、目标、任务、依赖和 attempt。
- 状态机与三种推进策略。
- 任务包、manifest、receipt、artifacts 的导出和严格导入。
- 配置分层、协议版本和错误模型。

本阶段不做 Git 自动合并。

验收：可创建目标、拆分任务、分配给任意数量 Agent、导入回执、重启恢复；无效回执不会推进状态。

## Phase 2：隔离工作区、租约与验证

目标：允许多个 Agent 安全并行完成实际编码。

范围：

- Git worktree 生命周期与基线记录。
- 任务/路径租约和心跳。
- 允许/禁止路径检查。
- 声明式验证执行器、超时、取消和证据。
- 文件监听的稳定写入与幂等导入。

验收：两个 Agent 可并行修改不同范围；越权、过期租约和验证失败会阻止完成；失败可生成修复任务。

## Phase 3：审查、合并与恢复

目标：建立强模型审查和可恢复集成闭环。

范围：

- 集成 worktree 与串行 merge queue。
- review 请求、批准、要求修改和升级路径。
- cherry-pick/merge 冲突处理。
- 操作日志、崩溃恢复和显式回滚。
- worktree 安全清理与成果救援。

验收：冲突不会覆盖用户代码；崩溃后能判断 Git 操作真实状态；审查未通过不可合并；已合并任务可审计回滚。

## Phase 4：完整桌面交互

目标：让非命令行用户也能透明控制协调过程。

范围：

- 项目向导、动态 Agent 管理、任务板和工作台。
- 计划批准、回执、验证、审查、合并和恢复界面。
- 危险操作确认中心与策略配置。
- 中英文、桌面通知和可访问性基础。

验收：用户可仅通过 GUI 完成三 Agent 端到端流程；每个自动决策都可解释、暂停或接管。

## Phase 5：路由、上下文与成本优化

目标：用强模型的判断换取低成本模型的大量执行，降低贵模型 token 消耗。

范围：

- 能力/成本 profile 与推荐路由。
- 分层上下文、摘要、缓存和按需证据。
- retry、失败分类、升级和降级策略。
- token/费用估算、预算阈值和项目报表。

验收：真实演示“强模型规划 → 低成本实现 → 强模型只处理难点与最终审查”；报告可解释路由依据和 token 节省估算。

## Phase 6：多 Agent 稳定性与发布

目标：达到可供日常使用的可安装版本。

范围：

- 2–8 个 Agent 压力和并行测试。
- 通知、诊断包、迁移、安装和卸载流程。
- 性能、长期运行、权限和安全加固。
- 用户手册、故障恢复手册和示例项目。

验收：满足 [测试与验收规范](11-testing-and-acceptance.md) 的发布门禁；安装升级不会破坏已有项目；已知限制明确记录。

## 阶段交付清单

Reasonix 每阶段必须交付：

1. 本阶段实现说明和实际完成范围。
2. 设计偏差及原因；未经批准的偏差视为缺陷。
3. 修改文件列表。
4. 新增/修改测试列表和完整输出。
5. 手工验收步骤与证据。
6. 已知限制、安全影响和数据迁移影响。
7. 单一、可审查的提交或明确提交序列。
